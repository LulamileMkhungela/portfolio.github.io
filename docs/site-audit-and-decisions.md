# Site audit and content decisions

Scope: `index.html`, the desktop/Messages/Services/CV data in `js/`, and the 13 pages in `portfolio/`.
Sources used: the repository itself (CV content in `js/desktop.js`, testimonials, case-study pages),
the live Pages index, and Superhive's UX portfolio structure guidance
(https://www.superhive.co/ux-design-portfolio-projects-structure-recruiters-want).

## 1. Is the site ready for UI, frontend and UX recruiters?

**Strong:** a clear devsigner positioning in the About and Services text; real shipped products
(Vodacom Engage, Toyota apps, FoodieZone, LulaGazette, DesignOps); a real CV and certificate trail;
the case studies share a consistent section order (problem, goals, personas, process, impact, outcomes).

**Weak for a time-pressed recruiter (Superhive "scan" layer):**
- The homepage has no role-fit headline. A recruiter sees a desktop of folders before they learn the target role.
- The desktop metaphor needs an interaction to reach content. Recruiters will not explore it, so the case studies need to be reachable from a plain, linear entry point.
- Case-study narratives list problems and outcomes but seldom show *decisions with trade-offs* or *ownership boundaries* (the "credibility" layer).
- Several outcome numbers appear without a stated measurement method, and some CV figures have no matching case study (see section 4).

**Technical:** `js/desktop.js` is about 317 KB and loads jQuery plus about 256 KB of Timber. Lighthouse/RUM has not been run here, so treat load cost as unmeasured. The filter label duplication was fixed previously (`index.html`, `css/desktop.css` v=79).

## 12. Protected case studies and Vision Bin (this session)
- **Six confidential studies are now encrypted, not just hidden:** media scanning for audit, safety statistics, compliance AI assistant, coal stockpile forecasting, configurable chart components, configurable timeline view. `scripts/lock_case_studies.py` replaces each page body with AES-256-GCM ciphertext and a lock screen; `js/case-lock.js` decrypts in the browser (PBKDF2-SHA256, 310 000 rounds) when the password is right. Meta descriptions are replaced with a generic line and the pages carry `noindex`. A correct password is remembered for the tab (sessionStorage) so previous/next between locked studies works.
- **Workflow:** `python3 scripts/build_case_studies.py` regenerates plaintext; then `CASE_STUDY_PASSWORD='…' python3 scripts/lock_case_studies.py`. To rotate: `--unlock` with the old password, then lock with the new one. Requires `pip install cryptography`.
- **Caveat:** the plaintext of these pages exists in earlier commits on `main`. If the history must be clean too, rewrite it (for example `git filter-repo`) and force-push, or accept that the live site is protected but the repository history is not.

## 30. Why Phone / WhatsApp enquiries never arrived; wa.me handoff + Formspree hardening (user, this session)
- **Root cause — nothing was ever sent to a phone.** The `Phone / WhatsApp` radio only swapped which box the visitor filled in; the box is labelled **Your phone / WhatsApp number** — the *visitor's* number, collected as data. On submit the page did exactly one thing: `fetch("https://formspree.io/f/xvkgqalq", { … JSON … })`. Formspree is an email service and cannot send WhatsApp, and `+27837195064` appeared nowhere in the repo. The success panel said "Request sent / Thanks! I'll get back to you soon" for **both** channels, which is why it looked like it worked.
- **Real automated WhatsApp is not free and cannot be built into this static page.** Meta's Cloud API is free to access and (from 1 Oct 2026) gives 1,000 free **service** messages per phone number per month, but those only cover replies *inside* a 24-hour window the customer opens. A notification triggered by a form submission is business-initiated, so it needs an approved **template**, which is chargeable per message with no free allowance. It also needs a hosted relay (a Cloudflare Worker or similar) because the access token must never sit in client-side JS, plus a Meta Business account and a number registered to the API. The user chose the free route below instead.
- **What "Phone / WhatsApp" does now (wa.me handoff):** on a successful submit the success panel shows a **Send it on WhatsApp** button (`#ps-success-whatsapp`) linking to `https://wa.me/27837195064?text=…`. The pre-filled message carries **every captured field** — name, need, project, budget, timeline, the visitor's number and their email if they gave one. The page also attempts `window.open()` on the same URL, but browsers block a popup opened after an async `fetch`, so the button is the path that always works. The success note now says to press send in WhatsApp, and the modal intro reads "Fill this in, then choose how I get back to you — email or WhatsApp."
- **Failure path is now a handoff too:** if the POST fails and the visitor chose phone, a **Message me on WhatsApp instead** link (`#ps-form-whatsapp`) is revealed under the submit button with the same pre-filled link, so a broken form backend no longer loses the enquiry.
- **Formspree hardened (the "I see Request sent but no email" bug):**
  - The old code only checked `response.ok`, so a **200 with an error body** still showed "Request sent". It now parses the JSON and treats `data.error` as a failure, and the toast shows Formspree's actual message (`Couldn't send — <error>. Email mkhungela.l@gmail.com directly.`).
  - Payload gained `_subject` and `_replyto`. Subject lines are `Prompts request — <name> (<need>)` for email and `PHONE / WhatsApp request <number> — <name>` for phone, so the channel and the number are visible in the inbox subject without opening the mail. `_replyto` is set only when an email was given, so replying in Gmail goes to the visitor instead of Formspree.
  - Empty-body responses no longer throw (`response.json().catch(() => ({}))`).
  - Closing the modal clears both WhatsApp links and the success note (`hideWhatsAppHandoffs()`), so a stale `wa.me` URL with the previous visitor's details can never be reused.
- **Not changed:** the 23 case-study "Let's Collaborate" forms still post to `../php/send-email.php`, which does not exist in this static repo, so they still fall back to opening the visitor's mail app (`js/contact-form-fallback.js`). The user was asked and chose to leave them for now.
