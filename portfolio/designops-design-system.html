DesignOps

One design, every framework.

IndustryDesign systems & developer tooling

This one is mine. Design systems drift because the same token ends up in two places, so I built the pipeline that stops it — and the linter that proves it. Figma variables export to forty-one W3C DTCG tokens, Style Dictionary builds fourteen targets from them, and @designops/lint checks shipped code against the system. I designed the token model, wrote the pipeline, and documented the lot.

One source of truth, fourteen targets — zero design drift.

Every team says it has a design system. Most have a Figma file that quietly drifts from what is actually in production. DesignOps was built to close that gap: Figma variables are treated as the input, tokens JSON as the single source of truth, and Style Dictionary as the machine that produces usable output for React, Vue, Angular, Svelte, Next, Nuxt, Remix, Astro, Ionic, MUI, Tailwind and the rest. The dashboard is the workspace where that pipeline is visible and usable — ten views with zero build step, from tokens and components to the advisory catalogue, the demo gallery, a live lint playground and the request board.

It is also a statement about how I work: design decisions should be expressed once, in a form code can consume, and then verified everywhere they land. The advisory proposes, the tokens record, the linter checks — and when they disagree, the linter wins.

The work followed the product design and front-end process end to end: discovery, audit and token model, advisory, build, proof and verify.

Designed, built and documented by LulaMile-HalfMachine.

Goals

BUSINESS GOALS

What the business needed

  • Make one source of truth authoritative: change the token once, ship it everywhere.
  • Remove manual translation between design and every framework the team uses.
  • Give the system a visible pipeline so drift is obvious instead of discovered in review.
USER GOALS

What people needed

  • Find the right component or token in seconds, by name, token or framework.
  • See what each framework build will actually output before wiring it in.
  • Read the usage rules where the component lives, not in a separate document.

Process

Advise, tokenize, build, verify.

6 stages — Discovery → Audit & token model → Advise → Build → Prove → Verify.

01 · Discovery

Where the handoff breaks

Before any code, the work mapped where design and development drift apart, and for whom. Two users defined the brief: the designer who specs 16px, and the developer who types 15px at 11pm on a deadline. The failure points were mechanical — values re-typed by hand, frameworks that cannot express a style so developers improvise, the same component rebuilt slightly differently per stack, requests lost in Slack threads, and docs that rot the day they are written. Each one became a requirement.

02 · Audit & token model

Forty-one tokens, one meaning

The system was audited first: which tokens were real, which had drifted, and which frameworks had quietly invented their own. The model that came out is forty-one W3C DTCG tokens — primitives, semantic roles and component-level values — so a name means the same thing in Figma, in CSS, and in a TypeScript constant.

03 · Advise

A direction before a decision

A vendored design-intelligence catalogue — 79 searchable styles, 192 product palettes, 74 font pairings and 119 UX guidelines, searchable offline — turns a direction like "dark fintech dashboard" into a W3C DTCG token proposal. Every proposal ships with a provenance map of where each token came from, seven WCAG contrast checks, and a record of what deliberately did not become a token. The advisory proposes; it never writes the source of truth.

04 · Build

One source, fourteen targets

tokens.json stays the single source of truth, and Style Dictionary transforms it into CSS, SCSS, TypeScript and Tailwind artefacts, with components generated for all fourteen framework targets from that one file. The dashboard puts the whole system on screen in ten views with zero build step — tokens, components, frameworks, advisory, demos, a live lint playground, the request board, Storybook and integrations. Dev asks, designer designs, one approval ships it to every target.

05 · Prove

Forty sites, zero findings

The proof is a gallery of forty generated sites across twenty categories, built from the components themselves rather than styled by hand. Each page is emitted twice from the same template — the HTML you open and the JSX the linter checks — so a finding is a finding about the page, not about a separate copy. Every site carries its own palette and font pairing, zero lint findings, and its measured contrast, reported rather than quietly fixed.

06 · Verify

The linter outranks the catalogue

@designops/lint runs six rules in ESLint and Oxlint — no restyling system components, no raw colours, no arbitrary values, no inline styles, no unknown classes, no unreadable class values. Every diagnostic explains itself and suggests a fix drawn from the team's own theme. Dashboard smoke tests and a freshness gate fail the build if the generated artefacts ever drift from the tokens, so a broken value never reaches production.

Impact

Verifies, not just ships.

The loop runs end to end: the advisory proposes a direction, forty-one W3C DTCG tokens record the decision, Style Dictionary builds every target, and @designops/lint checks the result — when they disagree, the linter wins. Search reaches components, tokens, frameworks and requests in one dashboard, and the export step hands a build exactly the artefact it needs — no re-entry, no guessing at what the current value is.

The practical result is that a design change is a commit rather than a conversation, a lint failure is a design decision caught by the pipeline instead of in review, and the dashboard documents the system as it actually is, not as it was described in a slide six months ago.
