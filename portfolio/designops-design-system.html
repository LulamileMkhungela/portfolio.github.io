The problem

Every team says it has a design system. Most have a Figma file that quietly drifts from what is in production.

Design and code drift apart
A token changes in Figma, a value gets hard-coded in one app, and within a release or two nobody can say what the real spacing scale is.
Every framework needs the same tokens, differently
CSS custom properties, Tailwind config, SCSS maps and TypeScript constants all express one design decision four different ways.
Nobody can find the component they need
Components are scattered across files, stories and tickets, with no single place to search by name, token or framework.
Documentation is the last thing updated
Usage rules live in people's heads or in a document from two renames ago.

Who it is for

The design system maintainer
Owns the tokens and components, and wants to publish a decision once and know every framework picks it up.
The front-end developer
Wants the right token, in the right format, with the usage rules attached, instead of a hard-coded hex.
The engineering lead
Wants to see that a UI change came from the token source rather than a hand edit.

Decisions

1. One source of truth: the tokens

Figma variables are the input, and tokens.json is the single source of truth. Style Dictionary builds the output for every target from that one file. The model is 41 W3C DTCG tokens, covering primitives, semantic roles and component-level values, so one name means the same thing in Figma, CSS and TypeScript.

2. The advisory proposes; it never writes

A design-intelligence catalogue turns a direction, such as "dark fintech dashboard", into a token proposal. Each proposal includes a map of where each token came from, seven WCAG contrast checks, and a record of what was deliberately not made into a token. A person approves the proposal before it touches the source.

3. When the advisory and the linter disagree, the linter wins

@designops/lint runs six rules in ESLint and Oxlint: no restyling system components, no raw colours, no arbitrary values, no inline styles, no unknown classes, and no unreadable class values. Each diagnostic explains itself and suggests a fix from the team's own theme.

Process

1. Discovery
Mapped where design and development drift apart, and for whom.
2. Audit and token model
Found which tokens were real and which had drifted.
3. Advise
Turned a direction into a token proposal.
4. Build
One source, fourteen framework targets.
5. Prove
A gallery of forty generated sites.
6. Verify
The linter checks the result.

In the product

The dashboard is the workspace where the pipeline is visible. It has ten views with no build step, covering tokens and components, the advisory catalogue, the demo gallery, a live lint playground and the request board. Search reaches components, tokens, frameworks and requests in one place.

Outcome

A design change is a commit rather than a conversation, and a lint failure is a design decision caught by the pipeline instead of in review.
